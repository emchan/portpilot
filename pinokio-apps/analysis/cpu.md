# CPU-only execution across the Pinokio Factory apps

Companion to [`results/pinokio-apps.md`](../results/pinokio-apps.md), [`analysis/flows.md`](flows.md), [`analysis/kernels.md`](kernels.md), [`analysis/quantization.md`](quantization.md), [`analysis/fusion.md`](fusion.md) and [`../flows/`](../flows/). Every project row links to its analysed `main`-tip commit from 2026-11-20 and, where useful, to the reconstructed matmul flow.

CPU-only here means: install the PyTorch/ONNX stack from a CPU wheel index, run the app with no NVIDIA/AMD/Apple GPU, and execute every model operator on the host CPU. An app can be CPU-*capable* yet far too slow for its default checkpoint; those cases are called out explicitly.

## At a glance

| Verdict | Count | Meaning |
|---|---|---|
| CPU-native / no GPU compute | 11 | Pure web UIs, automation or media tools; no local GEMM workload in the snapshot. |
| CPU-capable with shipped fallback | 68 | CPU wheel branch and/or explicit device fallback exists; works, often slowly. |
| CPU possible after launcher change | 9 | No CPU branch is wired up; upstream or launcher edits are needed first. |
| Hard-blocked on CUDA | 5 | Requires TensorRT, CUDA Graphs or compiled CUDA extensions with no CPU implementation. |
| Apple-silicon runtime only | 6 | MLX-based; Apple CPU/GPU only, not a generic x86 CPU host. |
| Empty repository | 2 | No code to analyse. |

The single strongest signal is a `download.pytorch.org/whl/cpu` route in `torch.js`: **68** projects have one. A further **8** have an explicit CPU device branch in application code and **27** use `devicetorch`, which resolves to CPU when no accelerator is visible. Only **4** projects contain a source-level CUDA requirement/guard, and only **1** imports TensorRT/CUDA runtime unconditionally.

## 2. CPU-capable with the shipped fallback

The launcher installs a CPU PyTorch wheel (or a non-GPU default wheel on Windows) and the app either uses `devicetorch`, an explicit `else 'cpu'` branch, or framework defaults that work on CPU. The GPU-only attention/quantisation wheels live inside NVIDIA-specific branches and are not installed on a CPU host. The main limitations are throughput and dtype support, not missing operators.

## 6. What the flows say about CPU support

The 22 projects with reconstructed checkpoint flows contain **43,886** matrix/conv/attention ops. All of them map to CPU-executable *operator classes*; the blockers are dtype and kernel-library choices rather than missing mathematics.

| Flow operation | Count | CPU backend | Verdict |
|---|---|---|---|
| Matmul (linear) | 29,458 | oneDNN/MKL GEMM | Fully supported; FP32 is fastest on generic CPUs. |
| LoRA low-rank matmul | 7,476 | two small GEMMs | Supported; fold into base weight on CPU to avoid two passes ([`fusion.md`](fusion.md)). |
| Conv / 1x1 conv (im2col) | 6,784 | oneDNN convolution/im2col | Supported; channel-last layouts help AVX512/AMX. |
| Attention scores + context | 168 | SDPA MATH/oneDNN backend | FlashAttention/SageAttention/xformers are CUDA-only; force the SDPA math backend. |

### Dtype mapping for the reconstructed GEMMs

| Weight dtype | Flow GEMMs | CPU support | Action |
|---|---|---|---|
| F32 | 10,007 | Native FP32 GEMM (MKL/oneDNN) | Best CPU dtype; use `--precision full --no-half` where a launcher exposes it. |
| F16 | 22,240 | oneDNN FP16 / upcast to FP32 | Works but generic CPUs gain little; fast on AVX512-FP16 (Sapphire Rapids). |
| BF16 | 6,486 | oneDNN BF16 / AMX | Fast on AVX512-BF16 or AMX; emulated via FP32 elsewhere. |
| F8_E4M3 | 3,733 | No native CPU FP8 GEMM | Upcast FP8 blocks to BF16/FP32; only `comfy` and `stable-diffusion-webui-forge` flows are affected. |
| U8 (packed 4-bit / NF4) | 1,252 | Dequantise then GEMM | bitsandbytes/torchao GPU quantisers are not a drop-in CPU path; GGUF Q4_K_M with llama.cpp is. |
| Unspecified | 168 | Inspect checkpoint at runtime | Treated as FP32 for planning. |

[`../flows/`](../flows/) has the per-project A/B/C shapes and dtypes; use the Flow column in the tables above to jump to a specific app. The precision breakdown itself is in [`quantization.md`](quantization.md) and the model-level provenance in [`models.md`](models.md).

## 7. Optimizations that matter on CPU

| Optimization | Why it helps / where to apply it |
|---|---|
| Force the math/oneDNN attention backend | Set `torch.nn.attention.sdpa_kernel(SDPBackend.MATH)` or disable `xformers`/`flash-attn`/`sageattention` in config. The 168 QK^T/softmax·V ops then run through CPU SDPA; the CUDA kernels are skipped instead of failing. |
| Upcast FP8 and packed 4-bit weights once | For the 3,733 FP8 and 1,252 packed 4-bit GEMMs, dequantise to BF16/FP32 at load time rather than per call. For LLM-shaped apps prefer GGUF Q4_K_M via llama.cpp, as `Orpheus-TTS-FastAPI` already does. |
| Tune the CPU GEMM runtime | Keep `torch.backends.mkldnn.enabled = True`, set `OMP_NUM_THREADS`/`MKL_NUM_THREADS` to the physical core count and pin NUMA threads. This is the largest single win for the 29k linear GEMMs. |
| Use channel-last for convolutions | The 6,784 im2col/conv GEMMs benefit from `memory_format=torch.channels_last` with oneDNN on AVX512/AMX hosts. |
| Apply the fusion opportunities already catalogued | QKV (1,942 groups), MLP gate/up/down (3,604 matmuls) and linear+bias (19,873 pairs) from [`fusion.md`](fusion.md) reduce memory traffic, which is the dominant CPU cost. |
| Compile the CPU graph | `torch.compile` with the Inductor C++/OpenMP backend fuses pointwise chains and epilogues on CPU. Avoid `mode='reduce-overhead'`, which is CUDA-Graph specific. |
| Quantise linear layers to INT8 | Dynamic INT8 quantisation of the dominant linear GEMMs via oneDNN/torchao gives a further 2-4x on AVX512-VNNI or AMX; validate accuracy on the attention output and LM head. |
| Reduce memory pressure | For the large BF16/FP16 diffusion flows (e.g. `comfy`, `forge`, `Frame-Pack`) use attention slicing, tiled VAE and CPU offload; a 14B BF16 checkpoint still needs tens of GB of RAM. |
| Patch the few direct CUDA calls | The 11 projects with direct `torch.cuda` calls can use the `devicetorch` pattern already present in 27 repos, or the `cuda if available else cpu` branches used by `cogstudio`, `hertz` and `ovis`. |

## 8. Method and caveats

- Signals come from the 2026-11-20 snapshots: `torch.js` wheel routes, `install.js` start-up guards, Python device selection, GGUF/llama.cpp download steps and direct CUDA/TensorRT imports. Click any Commit column entry for the exact analysed SHA.
- A CPU wheel route proves the launcher can install CPU PyTorch; it does not prove a large checkpoint runs at interactive speed. Throughput caveats above are based on the dtype/shape mix in the flows, not on benchmark runs.
- GPUs other than NVIDIA are out of scope for this note: AMD ROCm, Apple MPS and DirectML are GPU backends, not CPU backends. See [`kernels.md`](kernels.md) for their coverage.
- Empty repositories `y` and `factory` have no commit and no evidence.
