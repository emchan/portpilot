# TPU suitability across Pinokio apps

Companion to [`results/pinokio-apps.md`](../results/pinokio-apps.md), [`kernels.md`](kernels.md), [`quantization.md`](quantization.md), [`fusion.md`](fusion.md), [`flows.md`](flows.md), [`cpu.md`](cpu.md), and [`effort.md`](effort.md). This note assesses whether each of the 101 Pinokio Factory launcher snapshots can run on **Google TPU** (TPU VM / TPU-backed PyTorch-XLA or equivalent TPU runtime), using the same snapshot evidence as the CPU analysis. It is a source-snapshot suitability assessment, **not** a TPU runtime benchmark. All snapshots were taken from the default branch `main` on 2026-11-20; per-repository analyzed commit SHAs are recorded in [`../results/<repo>.md`](../results/) and linked in the tables below.

## TPU porting assumptions

- **Runtime.** “Possible on TPU” here means feasible through a TPU-supported ML runtime, typically **PyTorch/XLA** for PyTorch apps, after replacing CUDA wheels and device assumptions. It does **not** mean the existing CUDA wheel/install path works unchanged.
- **Device abstraction.** `torch.cuda`, `.cuda()`, CUDA streams/events, CUDA Graphs, and hard-coded `cuda` device strings must be replaced with accelerator-agnostic device selection or XLA device placement.
- **Attention/kernels.** xformers, FlashAttention, SageAttention, Triton kernels, CUDA Graph capture, and TensorRT engines are CUDA/GPU-specific in these snapshots. TPU ports must fall back to XLA/SDPA/Pallas-compatible kernels or remove the optimization.
- **Quantization/dtypes.** BF16/FP16/FP32 are generally TPU-friendly; FP8/NF4/bitsandbytes/torchao GPU paths need validation, upcast/dequantization, or TPU-supported quantized kernels. GGUF is a container format, but CUDA-specific GGUF loader wheels are not TPU-ready.
- **Scope.** This evaluates local model/runtime portability. Apps with no local GEMM workload can run on CPU/control-plane hosts alongside TPU services but do not benefit from TPU acceleration.

## Flow and dtype implications for TPU

The reconstructed flow data in [`flows.md`](flows.md) covers **43,886 matmul operations** across 22 projects with safetensors checkpoints. TPU suitability follows the same operator classes, but the kernel/dtype constraints differ from CPU:

| Flow operation | Count | TPU outlook | Notes |
|---|---:|---|---|
| Matmul (linear) | 29,458 | Good fit | TPU is strong at dense matmuls; main work is XLA device placement, static/dynamic shape behavior, and BF16/FP32 numerics validation. |
| LoRA low-rank matmul | 7,476 | Good fit | Supported as matmuls; consider folding/adapters and XLA compilation overhead. |
| Conv / 1x1 conv (im2col) | 6,784 | Usually portable | Common in diffusion/VAE/UNet paths; validate layout, padding, and XLA compilation. |
| Attention scores + context | 168 | Portable with fallback | Replace FlashAttention/SageAttention/xformers with TPU-compatible attention/SDPA/XLA kernel; validate masking and numerics. |

| Weight dtype | Flow GEMMs | TPU outlook | Action |
|---|---:|---|---|
| F32 | 10,007 | Supported | Easiest correctness baseline; may be slower/more memory intensive than BF16. |
| F16 | 22,240 | Usually supported | Validate numerics and XLA op coverage; BF16 is often preferred on TPU. |
| BF16 | 6,486 | Good fit | Natural TPU dtype for many models; validate quality-sensitive layers. |
| F8_E4M3 | 3,733 | Needs validation | Upcast to BF16/FP16/FP32 unless using a TPU runtime/kernel path with proven FP8 support for the exact model. |
| U8 (packed 4-bit / NF4) | 1,252 | Difficult | Dequantize to BF16/FP16/FP32 or use a TPU-supported quantized format/runtime; bitsandbytes NF4 CUDA paths are not drop-in. |
| Unspecified | 168 | Inspect at runtime | Treat as unknown until checkpoint/runtime dtype is confirmed. |

## Recommended TPU pilot order

Start with low-risk apps before large diffusion/quantized stacks:

1. **Control/no-GEMM apps** (`open-webui`, `sillytavern`, `bolt`, `browser-use`) as deployment/control-plane smoke tests around TPU services.
2. **Small/plain PyTorch models** (`vibevoice-realtime`, `RMBG-2-Studio`, `cube`, `oasis`, `text2midi`, `omniparser`) for first PyTorch/XLA bring-up.
3. **Moderate CUDA-kernel-fallback apps** (`sd35`, `clarity-refiners-ui`, `flux-webui`, `Frame-Pack`) after SDPA/XLA attention fallback is proven.
4. **Quantized/large stacks** (`comfy`, `stable-diffusion-webui-forge`, `wan`) only after dtype/quantization strategy is decided.
5. **Avoid as first pilots**: hard CUDA/TensorRT/compiled-extension apps (`StreamDiffusion`, `TRELLIS`, `Allegro-txt2vid`, `ai-toolkit`, `hunyuanvideo`) and Apple MLX-only apps.

## Method and caveats

- Signals come from the 2026-11-20 snapshots and existing study artifacts: [`results/pinokio-apps.md`](../results/pinokio-apps.md), [`kernels.md`](kernels.md), [`quantization.md`](quantization.md), [`fusion.md`](fusion.md), [`flows.md`](flows.md), [`cpu.md`](cpu.md), and [`effort.md`](effort.md).
- A "possible" TPU classification means no hard CUDA source blocker was identified in the snapshot; it does **not** prove XLA op coverage, numerical parity, or acceptable performance.
- Many launchers install optional CUDA wheels (`xformers`, `flash-attn`, `sageattention`, `triton-windows`) behind flags; TPU ports should disable those flags and verify the fallback path is actually used.
- Direct `torch.cuda` calls, CUDA-only wheels, DeepSpeed, ONNX Runtime GPU, and custom CUDA extensions are the main practical blockers. The per-app blocker column carries the snapshot-specific evidence.
- Empty repositories `factory` and `y` have no runtime evidence.
