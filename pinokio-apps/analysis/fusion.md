# Kernel fusion: what is used today and what is ready for it

Companion to [`results/pinokio-apps.md`](../results/pinokio-apps.md), [`kernels.md`](kernels.md), [`flows.md`](flows.md), and [`tpu.md`](tpu.md). This note separates **fusion that the snapshots actually invoke** from **fusion opportunities inferred from the same checkpoints and source files**. All 101 repositories were scanned at their default-branch `main` snapshot taken on 2026-11-20; every evidence line links to the exact analysed commit recorded in `results/<repo>.md`. Unlike the earlier launcher-level scans, this scan also descends into vendored directories named `models/`, where most of the real model code lives; where that changes the picture relative to [`kernels.md`](kernels.md), prefer this deeper source-level evidence.

Fusion here means several arithmetic operations being executed by one kernel or one engine graph: a compiler/epilogue fusion (`torch.compile`, Inductor), a fused kernel (SDPA/FlashAttention/SageAttention/xformers, `baddbmm`, approximate GELU), a graph engine that fuses layers at build time (TensorRT, ONNX Runtime), or CUDA Graph capture that removes per-kernel launch overhead. Simple mixed-precision casting is covered in [`quantization.md`](quantization.md), not counted here.

## Fusion used in the snapshots

### Compiler-driven fusion

`torch.compile` lets Inductor fuse pointwise epilogues into the preceding GEMM or convolution. Only one wrapper calls it directly, and that call is turned off in the shipped Gradio app; three other launchers pass a `--compile` flag to upstream code, and zonos ships a patched Inductor C++ code generator that counts fused epilogues. `diffusers-image-fill` only detects whether a module was already compiled.

### Fused attention kernels

**22 projects** have direct fused-attention code or a wheel install (4 direct-code, 8 unconditional, 10 opt-in); **4** more only mention one in a comment, a disabled flag, documentation or a model name. The four direct-code projects are Allegro-txt2vid (`xformers` plus SDPA), Nari-Dia-TTS (SDPA), StreamDiffusion (`enable_xformers_memory_efficient_attention()`) and diffusers-image-fill (SDPA compiled-module check, not a call). Everything else is a launcher wheel install (often gated by `args.sageattention` / `args.flashattention`) or a requirements pin. These are the same kernels catalogued in [`kernels.md`](kernels.md); here the focus is their fusion effect (one kernel for scores + softmax + value matmul instead of three launches).

### Mechanisms that are absent

No snapshot contains `fused=True`, `FusedAdam`/`FusedSGD`, `_foreach_*` multi-tensor optimizer updates, `torch.quantization.fuse_modules`, `FusedLayerNorm`/`FusedBatchNorm`, `fused_bias_act`, `@triton.jit` kernels, FlashInfer/vLLM paged attention, or explicit `GraphOptimizationLevel` settings. The only `baddbmm` call is the Allegro one above; there are no explicit `torch.addmm` calls. This means almost all fusion in this collection comes from wheel-installed attention libraries, compiler flags passed to upstream apps, or graph engines — not from hand-written fused wrappers.

## Porting implications

- **Fused attention is the highest-value porting target.** SDPA has ROCm and MPS backends and is already used by Allegro-txt2vid and Nari-Dia-TTS; FlashAttention and SageAttention are installed as CUDA-specific wheels by most other launchers, so on AMD/Apple they must fall back to SDPA, MPSGraph/MLX attention or a new Triton/ROCm kernel. Allegro's `torch.backends.cuda.sdp_kernel(...)` context (allegro/models/transformers/block.py:834) is NVIDIA-only and must be made conditional.
- **Compiler fusion is the most portable route.** `torch.compile`/Inductor supports ROCm and has a growing MPS backend, so the zonos Inductor patch and Nari-Dia-TTS's decode-step compile hook are reusable; the three `--compile` launcher flags already delegate the work to upstream code. The shipped Gradio apps disable compile, so turning it on is a low-risk first experiment.
- **CUDA Graph capture has no direct MPS equivalent.** StreamDiffusion's captured TensorRT graph needs HIP graphs on ROCm and eager/graph alternatives on Apple; this is the single largest launch-overhead fusion to replace.
- **TensorRT layer fusion is NVIDIA-only.** StreamDiffusion's ONNX export is a useful intermediate that ONNX Runtime can fuse on other vendors (including the DirectML and ROCm ORT wheels already installed by facepoke/photomaker2), but the TensorRT engine builder and refitter must be skipped on those platforms.
- **Quantized-weight GEMMs are the hardest fused kernels to replace.** The LoRA, FP8 and NF4 opportunities counted above rely on dequantisation inside the GEMM epilogue; ROCm has partial equivalents (e.g. ROCm-aware bitsandbytes/hipBLAS), while MPS has no fused FP8/NF4 GEMM, so those paths need BF16 dequantisation before fusion.

## Method and caveats

- Source evidence comes from a case-insensitive scan of text files in every snapshot, including vendored `models/` directories; each hit is linked to the analysed commit with a `#L` anchor. A comment, a wheel install and a direct call are reported separately.
- Attention-pair, QKV, MLP and LoRA counts come from the reconstructed matmul graphs in [`flows.md`](flows.md). An attention pair matches one `Q×Kᵀ` score op with one `softmax×V` context op at the same model/component/block/tensor/dtype. QKV groups require all three projections to share the same attention-module prefix and identical weight shapes; this avoids pairing cross-attention Q with self-attention K/V.
- Weight/bias and Conv/bias counts come from safetensors headers: a rank-2 (or rank-4) `*.weight` tensor whose name has a matching `*.bias` sibling. BN counts cover `*bn*` weight/bias/running-stat tensors. Counts are per project because models are shared between launchers.
- These are opportunities inferred from static checkpoints and wrapper code, not profiled results. The upstream frameworks imported by the launchers may already fuse some of these operations at runtime; that cannot be verified from a launcher snapshot alone.
